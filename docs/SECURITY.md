# Security

This document describes the security model as implemented. Reporting procedures are in the root [`SECURITY.md`](../SECURITY.md); this file explains what the system defends, how, and where the boundaries currently stop.

## Trust boundary

```text
public internet → nginx gateway (:18000) → api (:8000) → PostgreSQL / object storage
```

- The gateway is the only component that publishes a port in the demo deployment. `deploy/docker-compose.demo.yml` removes the published API, database and MinIO ports with `ports: !reset []`, which requires Compose 2.24 or newer.
- The API trusts the gateway for transport metadata but does not trust any client-supplied identity beyond the current placeholder headers. Tenant and user values are read from `X-Tenant-Id` and `X-User-Id`; this is a Phase-3 placeholder to be replaced by token-derived identity.
- PostgreSQL and the object store are never exposed publicly in the demo overlay. In the local stack they are published on `5433`, `9000` and `9001` for development only.

## Gateway controls

`deploy/nginx/demo.conf`:

| Control | Configuration |
|---|---|
| Authentication | HTTP Basic Auth on `/ui/` and `/` (which covers `/v1`, `/live`, `/ready`, `/docs`, `/openapi.json`). Only `/health` is anonymous, and it proxies to `/live`. |
| Rate limiting | `limit_req_zone $binary_remote_addr zone=demo_rl:10m rate=10r/s`, applied with `burst=20 nodelay`; rejected requests return `429`. |
| Request size | `client_max_body_size 50m`, matching the application's `MAX_UPLOAD_BYTES` default of 52428800 bytes. |
| SSE | `proxy_read_timeout 300s`, `proxy_buffering off` so streamed chat responses are not buffered. |
| Console caching | `/ui/` responses carry `Cache-Control: no-cache`. |

The API independently enforces the upload limit before any database or disk write, so a misconfigured proxy does not create a bypass. Basic Auth credentials are generated by `scripts/deploy_demo.sh` into `deploy/nginx/htpasswd` with mode `600`. The public showcase instance publishes its single shared credential pair in the README so anyone can try it; that account holds no secret, is rate-limited, and is rotated by regenerating the htpasswd file. Any deployment holding real data must generate a fresh pair and keep it private.

## Application authorization

Three checks are layered:

1. **Scope** — every knowledge-base operation verifies that the knowledge base belongs to the current tenant (`ensure_kb`). A missing or foreign knowledge base returns `404`, so its existence is not disclosed. Identifiers are restricted to `[A-Za-z0-9_-]+` before being used in object paths.
2. **Role** — privileged operations (evaluation runs, load tests, manual retries, audit reads) require `users.role = 'admin'`. Role comes only from the database; request headers cannot assert it.
3. **ACL tags** — chunks carry optional `meta.acl_tags`. Chunks without tags are public; tagged chunks require a non-empty intersection with the caller's `users.tags`. Administrators bypass the tag check but remain inside their tenant scope. The condition is applied in SQL for vector retrieval, so invisible rows cannot occupy `top_k`, and in memory for BM25.

## Row-level security

`migrations/versions/0007_rls_chunks.py` creates the login role `kb_app` with `NOSUPERUSER NOBYPASSRLS`, enables and forces RLS on `chunks`, and installs policy `p_chunks_tenant`:

```sql
USING (tenant_id = current_setting('app.tenant_id', true))
WITH CHECK (tenant_id = current_setting('app.tenant_id', true))
```

`current_setting(..., true)` returns `NULL` instead of raising when the setting is absent; `NULL` comparisons are false, so an unscoped query returns zero rows. `src/db/session.py` sets the value with `set_config('app.tenant_id', :tenant_id, true)`, which is transaction-local and does not leak across pooled connections.

Operational consequences:

- The application must connect as `kb_app` (or another non-superuser, non-owner role). Superusers and the table owner under `FORCE` semantics bypass or change policy behaviour; connecting as `kb` in production defeats the guarantee.
- A query that forgets tenant scope fails closed (0 rows) rather than returning other tenants' data. `PgVectorStore` also raises `MissingTenantFilterError`, which the API maps to `500 internal scope error` because it is a code defect, not a user error.
- Only `chunks` is protected by RLS today. `documents`, `knowledge_bases`, `ingest_jobs`, traces and audit tables rely on application-level tenant predicates.

## Content safety

`src/guard/injection.py` screens for prompt injection at two points:

- **Context ingress** — chunks whose text matches high-confidence injection patterns are excluded from the prompt but kept in storage for audit. If every chunk is excluded, the request is refused.
- **Answer egress** — the prompt contains a canary string that a correct answer never repeats. If the answer contains the canary or an injection pattern, the response is replaced with a fixed refusal that does not repeat the suspicious text.

The pattern set is deliberately narrow to avoid false positives on legitimate questions; it is not a general content moderation system.

## Secrets management

- `.env` holds model keys, database passwords and demo credentials. `scripts/deploy_demo.sh` creates it with `umask 077` and forces mode `600`. `.gitignore` excludes `.env`; never commit it, and never print keys in logs, tickets or screenshots.
- `deploy/nginx/htpasswd` is generated at deploy time and also excluded from version control.
- The application uses the restricted S3 account created by `minio-init`, which can only read and write the `rag-kb` bucket. MinIO root credentials are for initialization only.
- Rotate credentials after any exposure and after the initial demo setup. Switching SSH access to key-based authentication is expected for the host itself.

## Demo environment caveats

- The demo runs over **plain HTTP**. Basic Auth credentials and all request bodies travel unencrypted; treat the demo account as disposable and never place real or personal data in it. The demo dataset is synthetic.
- The demo has no user self-registration and no per-user password store; it relies on one shared Basic Auth pair at the gateway. Application-level user identity still comes from the `X-User-Id` placeholder header.
- Rate limiting is per client IP and in-memory at nginx; it is a coarse protection against accidental load, not a defence against a distributed attacker.
- Any real deployment must terminate TLS in front of the gateway, replace the header-based identity with token validation, and connect to PostgreSQL as `kb_app`.

## Reporting a vulnerability

Follow the root [`SECURITY.md`](../SECURITY.md): email the maintainer privately with a description, reproduction steps or proof of concept, the tested commit, and any suggested mitigation. Do not open a public issue. Acknowledgement is targeted within three business days, with fixes for confirmed issues within 30 days.
