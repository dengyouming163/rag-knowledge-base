# ADR 0005：三层隔离（作用域 + ACL + 数据库 RLS）

- **状态**：已采纳
- **日期**：2026-11-19

## 背景

只靠“查询里记得写 `WHERE tenant_id = ?`”是约定，不是保证：一条新写的查询忘了加，
就是跨租户泄露。而租户内还需要“部门 A 看不到部门 B 的文档”。

## 决策

三层独立防线，任意一层失效仍有兜底：

| 层 | 机制 | 失败表现 |
|---|---|---|
| 1. 作用域 | `tenant_id`/`kb_id` 缺失即抛 `MissingTenantFilterError`（映射 500） | 请求失败，无法上线 |
| 2. 文档 ACL | `meta.acl_tags` 与用户 `tags` 求交集；管理员可跳过，但仍受租户约束 | 返回空，不泄露 |
| 3. 数据库 RLS | `chunks` 启用 `FORCE ROW LEVEL SECURITY`，策略依赖 `app.tenant_id` | 返回 0 行 |

配套约定：

- 业务连接使用**非超级用户** `kb_app`（超级用户绕过 RLS）；
- 事务内用 `set_config('app.tenant_id', ?, true)`（事务级），防止身份在连接池里串号；
- 角色来自 `users.role` 列，**不接受请求头声明**，避免提权。

## 后果

**好处**

- 即使应用层写错，数据库也不会返回别人的数据（fail-closed）。
- ACL 与 RLS 各自可测：跨租户、跨库、越权、管理员边界四组验收用例。

**代价**

- 每条访问 `chunks` 的语句都必须带作用域，脚本/测试也不例外；
- 迁移与管理脚本需用属主账号（DDL 权限），与业务账号分离；
- 目前只覆盖 `chunks`，`documents`/`knowledge_bases` 仍是应用层过滤。
